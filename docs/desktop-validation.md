## 0.5.11 主动获取高清封面与标题隔离（2026-11-17）

- 增加 512 KiB / 1 MiB 封面上限（实验），默认保持 256 KiB。图片原始字节与 Base64 校验同步提升至 1 MiB；现有命令帧 4 MiB 限制保持。实际接收端兼容性待验证。
- 新增「设置 → 封面 → 主动获取 Apple Music 高清封面」，默认关闭，独立于歌词开关。使用播放器自身缓存中与当前精确 catalogue ID、标题、歌手、专辑、时长一致的官方图片地址，不搜索匹配。请求完成后再次核对同一个曲目 ID。
- 系统图先显示，高清图在后台获取、编码并补送；失败保留系统图，关闭恢复系统图，切歌及退出取消旧请求。只读查询播放器；本轮未操作手机或控制播放。
- Mac 自动测试通过，新增精确 ID / 元数据不符拒绝、可信图片域名/协议限制、图片解码、缓存只读查找、封面刷新不覆盖较新进度/歌词/标题、设置改变后拒绝旧编码等检查。SwiftUI 原生构建及设置布局检查通过。
- 生产读取器只读实测：当前 Apple Music 曲目取得 2048×2048 官方图；在 WebP、最大 2048、256 KiB 限制下实际编码发送图为 1024×1024、151918 字节。探针使用进程内临时偏好，未改变用户设置。这不是电视最终清晰度验收，也不保证所有曲目都可读取。
- 11 项媒体转发测试通过，其中新增歌词晚到、进度跳转/暂停、切歌后的实际序列化包标题与歌词字段隔离检查，0 失败。
- 最终包只读媒体探针在 1 MiB 档实测发送 2048×2048 WebP、603540 字节（同轮 256 KiB 档为 1024×1024）。包自检、签名、ZIP 完整性和 IPC 检查通过；IPC 覆盖 1 MiB 图片可接受及多 1 字节拒绝。电视对较大图片的显示效果尚待用户验证。
- 标题审计：源 title 原样作为协议 mTitle，带时间轴歌词独立发送为 mLrc；没有随歌词滚动替换标题。播放器上报的标题若已被改写，或接收端使用歌词替代标题显示，需要另外定位，不能用此审计保证所有接收端行为。本轮未添加冗余的“强制歌名”开关。

## 0.5.10 原生投放设置与 WebP（2026-11-17）

- 原生设置窗口可从「更多设置 → 投放设置…」、菜单栏右键及 ⌘, 打开；集中显示 AAC 音质、同步模式、媒体/歌词开关和封面设置。选择器使用 AppKit 原生菜单，不因媒体刷新重新创建菜单。
- 封面选项：JPEG（默认兼容）、WebP/PNG（实验）；最长边 256/512/1024/2048；大小上限 48/128/256 KiB；质量 80/90/100；默认保留符合所选格式和限制的原图。100% JPEG/WebP 不等同于无损；PNG 不使用质量值。
- 图片设置自动保存到独立应用偏好，当前曲目后台重新处理并补送，无需重连；音质/同步模式沿用停止投放后重新选择音箱的行为。界面显示实际输出尺寸/格式/大小和直传/编码状态；不宣称能获知接收端是否成功显示。
- 本地 FusionPlay 接收端的 `XiaomiPlaybackSnapshotReducer.kt` 明确识别 JPEG/PNG/WebP 的 mArt 数据，并注明官方常见 WebP。Android 官方文档说明平台支持 WebP，但设备自身的接收软件兼容性仍要实测。未修改手机。
- 系统 ImageIO 可解码 WebP，但本机未提供 WebP 编码；应用自带固定 libwebp 1.6.0 编码器，源码来自官方 release，SHA-256 固定在依赖清单。BSD 许可、PATENTS、AUTHORS 和构建配方随包交付；无需 Homebrew。WebP 编码库不可用时设置禁选，已有偏好会转用 JPEG 并显示原因。
- 缓存同时包含原图内容与设置，限制两张图和总成本；格式切换及晚到回调不得覆盖其他曲目封面。原始输入 8 MiB 和网络图片 256 KiB 硬上限保留。
- 自动检查：18 项媒体/协议/控制测试通过，Mac 图片/媒体/歌词测试通过（含真实 WebP 解码及颜色、原图直传、设置缓存区分）。打包、自检、签名、ZIP 和 IPC 检查通过；原生设置窗口布局预览和实际菜单入口通过。
- 当前歌曲在只读监听探针中由 JPEG 热切换为 WebP，输出 300×300 / 7672 字节，没有改变真实设置或播放器。随后正常打开 0.5.10，由用户修改设置并投到 ZrBox 5，反馈「清晰一些了」。只读核对当时格式为 WebP、最长边上限 2048、质量 90、大小上限 256 KiB，实际输出已随歌曲变化为 600×600 / 28 KB；这确认该设备本轮能显示 WebP，不把不同曲目的主观观感当成同图编码对照实验。
- 其他接收端 WebP、PNG 真机显示、每次格式切换时音频是否连续和长期稳定性仍未验收。

## 0.5.9 高清封面（2026-11-17）

- 用户反馈电视封面模糊。0.5.8 的系统封面先缩至最长边 512，再发送最长边 256、最多 48 KiB JPEG；只读检查时 Apple Music 提供 600×539 JPEG，原有发送链路会降至约 256×230。
- 0.5.9 读取和发送最长边改为 1024，不放大小图，保留原比例；优先 JPEG 0.9，复杂图片先降低编码质量，再逐档降低尺寸，输出始终不超过 256 KiB。原始输入仍限制 8 MiB。
- 图片解码和发送用 JPEG 编码在媒体读取后台进行，以原始图片字节的 SHA-256 缓存最近两张处理结果；主线程只转发已编码内容。缓存有大小上限，不落盘。进度更新仍实时转发；音箱网络通道仅在媒体内容发生变化时发送封面。
- 共享核心同步调整 Base64 和解码后的图片大小校验；MiPlay 帧上限及写入超时保持原有值。新增高分辨率/长宽比/高复杂度图片与缓存复用验证，以及 256 KiB 封面后的音量、歌词、切歌和清空测试。
- 自动检查：原生图片/媒体/歌词测试通过；17 项媒体转发和运行循环测试通过，0 失败。新包自检、签名、ZIP 和 IPC（包括 256 KiB 图片接受与超限拒绝）通过。只读检查实际封面输出为 600×600 / 132265 JPEG 字节；已打开 0.5.9。
- 用户随后反馈：0.5.9 除封面仍感觉有点模糊、似乎略有改善外，其余显示、切歌、声音和音量调节正常。清晰度提升尚无明确主观确认；未把修改编码上限等同于电视显示改善。

## 自动验证边界

- 协议、封包、时钟与会话测试不等于实机听音。历史 Evidence 常量测试也不是新的真机验证。
- 原生音频转换测试使用生成的测试信号，不读取系统播放内容。
- 实际 AAC 集成测试将生成的 PCM 编码后再解码，检查声道、时长、能量和子进程退出。
- 测试中的网络仅使用本机回环地址；不自动连接局域网音箱。
- Windows 可交叉编译和打包，实际启动、WASAPI、aac_mf 与防火墙行为必须在 Windows 验证。
- 当前 Mac 测试包采用临时本地签名，没有 Developer ID 签名与公证。

## 真机验收步骤

1. 记录应用提交、系统版本、硬件型号、音箱固件以及连接网络；确认观察的是选中的音箱。
2. 初次启动只发现设备；点选音箱卡片后才申请采集权限并发送音频。分别测试音乐客户端和浏览器。
3. 确认电脑保持播放，音箱实际可听；记录端到端延迟，不用界面缓冲量代替。
4. 连续播放 2 小时，记录是否卡顿、断连或延迟不断增大；保留诊断导出。
5. 开始／停止 20 次，检查编码进程退出、采集停止、音箱释放。
6. 切换默认输出、断网重连、音箱重启、被其他设备占用、系统休眠唤醒、拒绝权限后重试。
7. 在无 .NET / FFmpeg 的机器验证测试包启动。Windows 首次使用允许程序在专用网络通信；不要整体关闭防火墙。
8. 完成后填写“通过 / 失败 / 未验证”、错误现象和对应提交，不将理论支持写为已验证。
