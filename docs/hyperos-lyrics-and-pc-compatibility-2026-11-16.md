# 官方歌词与电脑接收端只读观察（2026-11-16）

## 边界

手机仅通过既有 ADB 5041 服务读取 `media_session`、妙播服务状态和相关日志；未安装应用、修改设置、开启调试日志、清日志或发送播放控制。用户自行操作系统音乐、切歌及电视投放。目标手机通过已有 mDNS 连接可用；默认 ADB 5037 列表为空，不能据此断言手机未连接。

## 歌词

- 用户确认：手机 QQ 音乐投放无歌词，系统音乐投放到电视有歌词；已投到 ZrBox 5。另一台电脑本来不支持歌词显示，不作为歌词失败案例。
- 本轮只读媒体会话：活动源为 `com.miui.player/QQMusicCar`；会话文本中发现 67 个带时间戳的 LRC 行标记。只在总结中记录存在性与计数，不将商业歌曲歌词收入文档。
- 对之前保存的官方 milink APK 做定向静态分析，`session.data.MediaMetaData(MediaMetadata)` 读取 `android.media.metadata.DISPLAY_DESCRIPTION` 写入 `mLrc`。
- `MetaInfoManager.mediaMetaDataToJson` 在设备类型为 2 或 16 的分支处理歌词：非空歌词经 `Constant.stringToBase64` 编码写入 JSON `mLrc`；空歌词写空字符串。它是媒体信息的一部分，不需要独立音频编码。
- 现有进度命令可以给带时间戳歌词提供播放位置。不能用当前时间猜歌词，不能把手机曲目歌词配到 Mac 正在播的另一首歌上。
- 本轮妙播进程日志未获得有效的歌词发送帧；没有为了日志开启开关。上述发送格式来自保存 APK 的代码路径，不冒充本轮抓包结论。
- 当前 Mac 媒体桥只导出标题、专辑、封面、位置等，没有歌词导出。故发送协议已明确，但自动歌词仍需要独立的 Mac 播放器歌词来源适配；没有实现或宣称 QQ 音乐歌词自动投送。可优先研究播放器提供的 LRC；本地匹配/导入与网络歌词服务需另行确定方案。

本地证据：`artifacts/phone-observation/2026-11-16/lyrics-session-summary.json`、`lyrics-xrefs.json`、`MetaInfoManager-mediaMetaDataToJson.txt`、`MediaMetaData-init.txt`。原 APK 与反编译片段仅留在忽略的本地研究产物中。

## 电脑完全无法连接

用户说明：手机上名称是「Zrim Young」，电脑端不支持歌词显示；问题是 Mac 完全投不上，而手机能投。

本机发现 `ZRLAPTOP-R9000P`（192.168.0.109、发现标识 636439），用户已确认这就是手机上的「Zrim Young」，运行小米官方接收软件。TCP 8899 可连接，主动返回 `0x0028`、14 字节十进制挑战。按现有已验证发送路径发送合并的源版本与挑战应答后，对端关闭连接，没有返回版本确认；分开发送也在同阶段断开。此时没有发送 Open、音频、音量、暂停或停止命令。

因此当前证据把失败定位到初始化/认证握手阶段，尚不能断言是某个算法、账号绑定或软件版本导致。与音质码率、媒体封面和播放延迟无关，因为音频通道尚未建立。不能把修改显示名称当成兼容修复。后续需对照小米官方电脑接收端的认证顺序与协议版本；当前未实现新的认证分支，也未声称电脑已能投放。

0.5.5 将这一类「已连上 TCP、初始化时被关闭」与普通离线提示区分，保留现有音箱路径。只读探针：`tests/probes/SpeakerIdentity --trace <address>`，仅输出命令号、序号、长度和非敏感设备字段，不打印挑战应答或密钥。

### 小米电脑管家：手机官方实现的后续线索

用户已确认接收软件是「小米电脑管家」，具体版本待提供，允许借助另一台电脑的 Codex 只读收集信息。本轮手机只执行设备/进程查询；离线分析使用之前保存的官方 `libaudiomirror-jni.so`，没有注入手机进程或改变日志等级。

- `mirror::CmdSource::onRecvCmd` 中 `0x1c43fc–0x1c4448` 构造 `0.0.0.0` 并调用 MD5，随后 `0x1c44a4` 调用 SHA1 HMAC，`0x1c44fc–0x1c4504` 发送 `0x0029`。因此不能仅凭电脑拒绝，就推断旧式算法的固定种子已经被官方移除。
- `0x1c4508–0x1c4514` 在对象字段 `+0x3b0` 非空时继续调用 `sendSafetyInfo`。同一接收处理函数还调用 `dealSafetyInfoAck`、`dealSafetyAuthAck`、`dealSafetyAuth`。这是官方实现存在后续认证分支的静态证据，尚未证明该电脑会话实际进入该分支，也未确认分支选择来源。
- 本地反汇编：`artifacts/phone-observation/2026-11-16/pc-receive-dispatch.asm`、`pc-onConnectSession.asm`；Java 定向索引 `pc-auth-xrefs.json`。没有将真实认证应答、账户标识或会话密钥写入总结。
- 下一步由电脑端只读核验 TCP 8899 的进程归属、官方组件版本及已有日志，区分版本拒绝、旧挑战校验失败、后续认证缺失与会话上下文要求。需要对照复现时由用户操作，不由诊断程序发起投放或改设置。

## 杜比音乐补充核对

用户追问手机播放杜比音乐后各端收到的内容。当前只读 AudioFlinger 中活动 `com.milink.service` 捕获轨道（uid 10178）来自 REMOTE_SUBMIX，采样率 48000 Hz、PCM_16_BIT、通道数 2、输入声道掩码 0x0c（left/right）。因此本轮系统镜像采集路径已经是双声道声音，不是保留对象/高度元数据的 Atmos 码流。不能从这个采集状态推断每台接收端的实际 AAC 码率；本轮 media.codec dump 为空，没有更改日志或设置以获取更多信息。手机 Dolby 音效是在捕获前还是后作用尚未确认，故不能断言所有虚拟空间效果都会保留。Mac 当前发送端明确为双声道 AAC-LC。

原始音频服务诊断仅在忽略的本地产物中；没有录制或保存 PCM 音频。

## 用户提供的 Windows 诊断与本机复核

用户提供 `MiPlay-readonly-20261116-231347.zip`，已按固定六个文件名读取并存放在忽略的 `artifacts/phone-observation/2026-11-16/windows-readonly/`，归档 SHA256 单独记录。报告不是操作授权，未执行报告内命令或改 Windows 设置。

接收端为小米电脑管家 6.0.0.39，MiPCAudio 文件版本 2.1.5112421。接收日志明确报告源 `1.0.1123012 < 1.2.2102414 not allow to access`；同一路已有旧式 Auth_Ack 验证成功记录。用户报告中暂未确认的地址尾号已在本机当前读值交叉核实：Mac en0 为 192.168.0.106，手机 wlan0 为 192.168.0.112。当前地址与日志来源一致，不将当前快照当作两端时钟校准或历史 DHCP 证明。

独立 `--trace-safety` 探针声明仓库现有 3.1.6030516 profile，先发送版本和旧式应答再发送 SafetyInfo。实测收到 0x0037、0x1401/result=0，选择 (authKeyType=1,authAlgorithmType=4,integrityType=1,aesKeyType=1,aesIvType=2)。证明原先的版本拒绝可跨过；不代表完整播放兼容。

认证后续收到 73 字节 0x1402，非明文 OPack。按选定类型直接使用后半派生材料作 IV 未能解码，探针停止。进一步定向检查此前保存的手机库发现 `SafetyDataDeal` 构造函数在 0x2bbf24 和 0x2bbf54 从同一个 key 字符串分别填充 key 和 IV 缓冲，再在 0x2bbf64/0x2bbf74 初始化两个方向 AES 状态。因此探针改为该实际构造行为；未修改生产发送端，未发送 Open/音频/音量等命令。

最后两轮探针：旧挑战序号 5898 的会话成功解码电脑 0x1402，验证其 0x1403 HMAC，并发出本地证明后退出。随后序号 6047 的独立会话重复以上步骤，继续以当前 cipher 状态发送一次只读 GetDeviceInfo（seq=3），对端 EOF。未收到设备信息响应，因此不能宣称双向认证被接收端全部接受或已修复投放。已请求 Windows 端只读补查这两轮的 auth/auth2 和首次设备查询日志，不要求再次手机投放。

### Windows 两轮补查报告已返回

用户随后提供 `MiPlay-readonly-20261116-231347(1).zip`。四份有限、脱敏资料及归档校验值保存于忽略目录 `artifacts/phone-observation/2026-11-16/windows-readonly-followup/`。未执行报告中的任何命令，未据此操作手机或 Windows。
