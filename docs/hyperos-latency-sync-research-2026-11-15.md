# HyperOS 妙播低延迟与多音箱同步研究

日期：2026-11-15。桌面代码基线：`codex/cross-platform-miplay` / `5057ec2`，含此前尚未提交的 Mac 媒体信息修复。本轮新增研究记录和本地诊断工具，没有修改正在使用的投放协议或应用包。

## 结论

有可以用于优化桌面发送端的明确依据。优先级最高的是**让同一组音箱共享编码后的音频、媒体时间线及播放时间基准，并消除等待连接期间积压的旧音频**，而非单纯继续降低每台音箱的延迟数值。

- 当前官方组件中的多音箱路径共享音频帧和播放时间偏移；后加入设备继承组内偏移，并有历史帧补发路径。
- 该路径在 5 GHz Wi-Fi 下配置 `800,000 µs`，否则配置 `1,000,000 µs`。这是播放缓冲参数，**不是实测端到端延迟**，也不代表所有妙播传输路径都用同一配置。
- 我们的桌面端共享了系统采集，却仍为每台音箱单独编码、单独生成时间线。仓库的共享会话已经实现部分所需能力，但桌面入口没有使用它，不能把现有多选投放视为已经实现官方式同步。
- 用真实 FFmpeg 做的本地对照复现了启动旧音频积压。模拟连接等待 3 秒时，第一帧的输入年龄约 3 秒；使用投放前清理门控后约 56 毫秒。**这不是实际音箱听音测试，也不能直接宣称端到端延迟降低了 2.94 秒。**

## 2. 当前官方组件中确认的机制

### 2.1 播放缓冲进入共同时间偏移

`MultiMirrorControl.startMirrorImpl` 新建 mirror option 后调用 `NetworkUtils.isCurrentWifi5GHz`；两个分支分别将 `0xc3500` 和 `0xf4240` 交给 `setAudioPlayDelayTime`，即 800,000 和 1,000,000 微秒。该段在离线 smali 文本约 1970–2030 行。

JNI setter `0x1b3b54` 检查非负值，并写入 option key `0x10010a`。`MultiMirrorDisplay::updateTimeOffset`（`0x1ee394`）读取同一 option，缺省为 1,000,000；`0x1ee420–0x1ee434` 实际计算：

```text
groupTimeOffset = serverNow - firstNormalizedAudioPTS + configuredDelay
```

`serverNow` 来自 `getMirrorServerTime()` → `TimerWork.GetServerInstance().GetCurTime()`（`0x1ede74`）。随后保存组内偏移，并遍历成员把同一值交给每台发送器。**不是为每台重新从“连接成功时刻 + 各自音频第零帧”建立时间原点。**

旧版上游研究里的 option key 与当前版本不同；不能把旧二进制偏移或常量直接复制到当前组件。

### 2.2 相同音频、相同 PTS，后加入不重建整组时间线

- `MultiMirrorControl_writeData`（`0x1b49f4`）保留 Java 传入的音频 PTS，并进入原生分发函数 `0x1a3e10`。
- `0x1a3e3c` 保存这一 PTS；成员循环将相同音频内容、长度和 PTS 传给各成员发送器。这里观察到的是音频帧分发，**不是证实网络层使用 UDP multicast**。
- 首次参与分发的成员会进入 `0x1a508c` 历史帧重放路径，然后再收到当前帧。
- 历史表保存内容、长度、PTS 和标志；`0x1a3fdc–0x1a3ff4` 以当前 PTS 与最旧 PTS 的差值是否达到 1,000,000 微秒触发淘汰。可描述为约 1 秒的历史窗口，不能把它算成所有音箱额外增加 1 秒播放延迟，也不是跨任意时间跳变都严格限长的证明。
- `MultiMirrorDisplay::addMirror`（`0x1ed388`，关键 `0x1ed5e0–0x1ed5f4`）将组内已保存的 time offset 交给新成员。
- `deleteMirror`（`0x1ed804`）查找指定成员、调用该成员释放逻辑并从成员表移除；函数中没有重建其他成员时间原点的操作。这是局部函数证据，不代表已完整追踪所有上层退出分支。

因此可借鉴的结构是“组拥有采集、编码、时间线；音箱拥有自己的连接和音量”。后加入者追上同一段媒体时间，不让原有音箱跟着重新开始。

### 2.3 音频 PTS 与传输时钟分工

`MicRecorder.muxAudio` 用首个 `MediaCodec.BufferInfo.presentationTimeUs` 作为音频基准，同时记录 `elapsedRealtimeNanos()/1000`。后续先得到归一化 PTS，再比较实际经过时间与音频 PTS。如果落后超过 `0x32`，调整基准使 PTS 前移。这里单位是**微秒，阈值为 50 µs，不是 50 ms**。

`TSPacketizer::packetize`（`0x220668`，关键 `0x221090–0x2210ac`）读取当前 `ATimer::GetNowUs()` 并乘以 27，生成 27 MHz PCR。此处没有减去播放缓冲，也没有使用采集帧的原始时间戳。

应用上的约束：编码帧序号／媒体 PTS、采集时间、发送时刻必须分别维护。不能为降低表面延迟，把原始采集时间直接当成编码 PTS；连接预热、丢采集帧或暂停恢复时可能因此产生跳跃。已有 [上游时间戳研究](miplay-tablet-output-timestamps.md) 可参考，但本轮对关键公式重新核对了当前手机组件。

### 2.4 时间同步不是只设一次固定延迟

`TimerService::Sync`（`0x2965cc`）收发 40 字节时间包。缓冲区起点为栈 `sp+0x10`：第一次取时写 `sp+0x28`，第二次取时写 `sp+0x20`，所以实际包字段为：

| 包内偏移 | 含义 |
|---|---|
| `+0` | 客户端发出时刻 |
| `+8` | 客户端收到时刻，由客户端补入 |
| `+16` | 服务端发出时刻 |
| `+24` | 服务端收到时刻 |

`TimerAlgorithm::unitRound`（`0x293fcc`）与 `unitOffset`（`0x293f98`）对应：

```text
RTT = clientReceive - clientSend - serverSend + serverReceive
offset = trunc((1-p)*(serverReceive-clientSend) + p*(serverSend-clientReceive))
```

该库还含历史样本处理、`approxLine` 以及 `ClockSync::CalculatTime`（`0x291350`）的仿射时间映射 `base + trunc(scale*(localTime-localBase))`。这证实组件有校时／速率修正能力，**不能据此认定两台目标音箱固件使用完全相同的算法、重采样策略或参数**；手机库也包括接收端代码。

桌面发送端应先保证给接收端的时间服务、TIME_OFFSET 和 PCR 一致。不要把库里的接收端 NetEq / DelayManager 字符串误当成可以直接设置的发送端低延迟开关。

## 3. 与当前桌面调用链对照

| 项目 | 当前桌面行为 | 可用基础及接入缺口 |
|---|---|---|
| 采集 | `SharedDesktopAudioPlatform` 共用一个物理采集源，向每台独立 PCM 队列写入 | 已有正确的共享采集起点；各台队列仍独立读取、补静音 |
| 编码 | `NativeCastSession` 为每台建立 runner；`CastService` 请求不带 `SharedAudioSession` | 应按相同声道路线共用 AAC 输出，避免帧序列独立推进 |
| 初始时间基准 | 每台独立握手、PTS 从自己的起点开始，TIME_OFFSET 取各自 PLAY 的单调时刻 | `MiPlaySharedAudioSession` / `MiPlaySharedOutputTimeline` 已有组偏移、共享 PTS、晚加入与同步恢复逻辑，但未接入桌面流程 |
| PCR | standalone 用采集时间减用户设置延迟；共享路径用发送时刻的完整 27 MHz 时钟 | 两套方式是不同的兼容路径，不能只替换一个字段便宣称已对齐官方 |
| 时间包 | standalone 调用旧 `CreateResponse`，`+16/+24` 的语义与当前官方组件相反 | 已有 `CreateTabletResponse`，当前只在共享路径启用；字段差异需要修正验证，但两次取时相近，不足以单独解释秒级延迟 |
| 编码预热 | 先启动编码再等连接；12 帧 AAC FIFO 满后施加反压，PCM 输入没有独立在途上限 | `MiPlayEncoderOutputGate` 类及测试存在，但当前生产调用链没有实例化它；不能因代码存在就称已启用 |
| 发送节奏 | standalone 不使用共享路径的启动节奏表，积压输出会被连续读取发送 | 需同时检查输入年龄、发送突发和接收端缓冲；不能把共享路径 14 帧启动预缓冲算到 standalone 上 |
| 共享路径平台支持 | `MiPlaySharedRouteEncoder` 直接启动 `aac_mf`；共享会话启动要求至少 2 个成员 | 需注入编码器工厂，并支持从单台组开始再加入成员，不能直接打开现有类作为 Mac 成品功能 |

主要代码入口：[桌面会话](../src/MiPlay.Core/Desktop/DesktopContracts.cs)、[开始投放](../src/MiPlay.Core/Desktop/CastService.cs)、[共享采集](../src/MiPlay.Core/Desktop/SharedDesktopAudioPlatform.cs)、[发送 runner](../src/MiPlay.Core/MiPlay/MiPlayLegacySystemAudioSessionRunner.cs)、[共享组](../src/MiPlay.Core/MiPlay/MiPlaySharedAudioSession.cs)、[共享编码器](../src/MiPlay.Core/MiPlay/MiPlaySharedRouteEncoder.cs)。

## 4. 用户听音与只读快照

要求用户在 Mac 不投放时操作官方妙播：Pro 单台约 20 秒 → 加入另一台约 20 秒 → 取消 Pro、保留另一台约 20 秒 → 停止。

用户反馈：**“没有回声 不会中断”**。登记为这轮官方加入／退出的主观听音结果。先前截图可见 `ZrSpeaker Pro` 和 `ZrSpeakerStereo`；本轮没有重新核对这两个名称对应的硬件型号和固件，不补填推测值。

23:40:13–23:43:08（手机时间）约每 5 秒取得一次状态，共 36 次：

- 始终有一条 MiLink 使用的活动 remote-submix 输入，I/O handle 为 390，帧计数递增；48 kHz、双声道、16 位，HAL frame count 为 1024。
- 始终有 3 个不同对端的已建立 `8899` 连接。**控制连接数量不等于正在播放的音箱数量。**
- 用户回复后的 23:46:57 复查仍显示同一采集线程活动。

这组快照没有清楚标记各操作阶段，因此不能用它证明现场每一次加入／退出均未重建编码器，或判断“全部停止”的释放时刻。仅确认观察窗口内共享采集保持活动。HAL frame count、系统显示的 record-track latency 都不是从手机到音箱的声学延迟；听不出回声也不等于测得亚毫秒同步。

## 5. 可复现的本地启动积压实验

新增 [EncoderStartupAge](../tests/probes/EncoderStartupAge/README.md) 工具，直接使用当前核心中的 FFmpeg 适配器、12 帧 FIFO 与预播放门控类。输入为生成的正弦波，不读取真实系统声音，不连接手机／音箱，不发出声音。

环境：Apple Silicon Mac，.NET SDK 10.0.404，随测试包使用的 FFmpeg 8.0.1，`aac` / AAC-LC / 48 kHz / 双声道 / 256 kbps。FFmpeg SHA-256：`4d25dad03c7fd0cbedf07c9bced0b92faf14c8498edab9c1c160b44c5a4413e8`。

每种条件重复 3 次，共 18 次。模拟连接等待 100 / 1000 / 3000 ms，开始后再读取至少 750 ms。基线在开始后立即消费输出，**没有人为加入现有 standalone 不使用的发送节奏**。对照组在等待时持续读走预热输出，达到 readiness 后仅发布输入时间不早于 readiness 的帧。

下表是三次的中位数，单位 ms；“输入年龄”是合成 PCM 提交给编码器至本地消费编码输出的时间：

| 模拟连接等待 | 基线首帧输入年龄 | 门控首帧输入年龄 | 门控在就绪后等首帧 | 基线稳态输入年龄 | 门控稳态输入年龄 |
|---:|---:|---:|---:|---:|---:|
| 100 | 101.48 | 49.35 | 55.90 | 68.95 | 69.61 |
| 1000 | 1000.96 | 89.38 | 91.66 | 72.28 | 70.72 |
| 3000 | 3000.52 | 56.08 | 63.98 | 66.15 | 71.96 |

稳态列取每次开始后 500 ms 以后的帧年龄中位数，再对三次取中位数。3 秒基线中，队列对外仍只显示 12 帧，但开始后的 200 ms 内消费了 147 帧；对照组为 6 帧。这说明只看有界队列深度会漏掉上游管道／编码器中滞留的数据，以及启动后集中输出的情况。

解释边界：

- 证实了启动时旧内容可以积压，且门控可避免向新会话发布这些内容。
- 基线在本地消费端能够追上实时；不能把首帧 3 秒年龄写成稳定播放一直有 3 秒延迟。
- 没有网络反压、接收端播放调度、操作系统采集缓冲或解码波形对齐；FIFO 输入／输出时间关联沿用当前适配器，未扣除编码器 priming。数值不能替代端到端测量。
- 门控多等了约 56–92 ms 才产生第一帧新内容；它应与会话 PTS 原点一起接入，不能运行中任意丢 AAC 来追延迟。

原始 JSON 保存在忽略目录 `artifacts/research/hyperos-latency/startup-age.json`。工具可独立重跑，使用方式见其 README。

本轮验证：诊断工具构建 0 警告、0 错误，18 次编码实验完成；与时间包、时钟、共享输出时间线、编码门控及有序队列相关的 **75 个既有测试通过**。这没有替代 Windows 编码器及实际音箱测试。

## 6. 建议的落地顺序与验收边界

1. **先改会话结构。** 一个投放组从第一台音箱开始就拥有采集、编码器、媒体帧序号和主时间线。将共享编码器改为平台工厂注入（Mac `aac`、Windows `aac_mf`）；加入／移除成员不重启其他成员。复用现有共享组能力，但补足单台启动、取消加入、失败移除和整体退出的生命周期测试。
2. **在同一实验模式内对齐时间规则。** 统一 TIME_OFFSET / PCR / 时间包行为，保留已验证的兼容路径供对照。将编码输入年龄、编码在途帧、发送突发、重设时间线次数记录到诊断中；不再把 PCM 缓冲深度显示成实际播放延迟。
3. **处理连接预热。** 连续排空投放前编码输出，在正式发布时确定音频时间原点；限制在途输入，并区分启动丢弃与运行中的完整帧序列。先做暂停恢复、长握手、断网恢复测试，再做真机听音。
4. **保留每台设置，但区分两个作用。** “整组播放缓冲”控制抗网络抖动与总延迟；“单台同步补偿”只调该音箱的相对播放时刻。音量继续单独设置并按稳定设备 ID 保存。补偿有符号且必须受可用提前量约束，不能凭负数让尚未到达的数据提前播放。
5. **逐档测最低稳定缓冲。** 先从 1000 / 800 / 600 / 400 ms 等实验档位测试同一组设备，不把官方某分支的 800 ms 自动设为所有用户的最优值。分别记录本地输入年龄、实测总延迟、两音箱声学偏差和欠载／重连，而不是只报主观“更快”。

下一轮需要用户配合时：提供测试版后，在相同位置和网络下比较原模式与共享时间线模式；播放短脉冲或节拍，用外部录音比较两音箱到达时间，并记录单台／双台、后加入／移除、连续播放后的偏差。测总延迟还需有同一次录音中的源端参考声；两音箱之间的偏差不能当作端到端延迟。考虑音箱到麦克风距离差，并保留型号、固件和应用提交。

目前手机只读研究已经足以确定结构改动方向；缺少的是桌面实验路径与目标音箱的声学 A/B 结果，而非继续盲目重复手机操作。
